General Notes:
The overall structure reads fine, the four child trees (topLeftTree, topRightTree, 
botLeftTree, botRightTree) are named clearly so you know which quadrant is which. 
The comments above each branch ("Indicates topLeftTree" etc) help you follow the 
subdivision logic. InBoundary is a clean little helper and does exactly what the 
name says. The Node struct is simple and makes sense, position plus the game object.

Improvements:
A few naming things make this harder to read than it needs to be. 'n' is a one 
letter field name and it's used all over, something like rootNode would be clearer. 
The underscore param names (_data) don't match the rest of the codebase style. The 
Insert and Search methods repeat the same (topLeft.X + botRight.X) / 2 midpoint 
math over and over, pulling that into a midX/midY local would cut the noise a lot 
and make the quadrant checks easier to read. Also there's a blank default comment 
block in Search that says "quad of unit length" but it's actually the node-found 
case, the comment is copied from Insert and doesn't match.

CODE QUALITY REVIEW

Author of Review: Arav Bhagat
Date of Review: 10-26-2026
Sprint Number: 3
Files Being Reviewed: QuadTree.cs
Author of File(s): Sami

Notes:
The recursive insert/search structure is the standard quadtree approach and it's 
reasonable. That said there are some real correctness concerns. The big one is each 
node only holds a single object (the Node n field), so two objects that land in the 
same unit cell, the second one just gets dropped since it only writes when n equals 
default. For a collision system with lots of blocks/enemies that's going to lose 
objects. Using default(Node) as the "empty" sentinel is also risky, a real object 
sitting exactly at (0,0) would compare equal to default and get treated as empty. 
There's no Remove method either, so moving objects can't be updated, which matters 
a lot since the player and enemies move every frame. The repeated midpoint math is 
a maintainability smell too, easy to typo one of them.

Hypothetical Change:
Instead of one object per node, each quad should hold a small list of objects and 
only subdivide once it passes a capacity threshold (classic quadtree). That fixes 
the dropped-object problem. I'd also add a Remove or a Clear so the tree can be 
rebuilt each frame as things move, right now there's no way to update it. And swap 
the default(Node) sentinel for an explicit bool like hasNode so a valid object at 
(0,0) doesn't get mistaken for empty. Pulling the midpoint into midX/midY locals 
would clean up both methods at the same time.
